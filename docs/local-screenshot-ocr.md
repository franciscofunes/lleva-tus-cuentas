# Local screenshot OCR — Transactions, Banks and Portfolio

## Scope

LTC reads **PNG, JPG, or WEBP screenshots** in-browser, without sending screenshot pixels or OCR text to Lita, Firestore or any inference API. On Android/iOS, the **default v3 reader** is an independent [Tesseract.js](https://github.com/naptha/tesseract.js) Web Worker with Spanish language data, including all core/worker/model files hosted on the same LTC origin after an explicit action. The former [`runonweb/ocr`](https://github.com/midudev/runonweb.ai) PP-OCRv6 reader remains available as an **optional advanced mode** (Tiny ~6 MB, Small ~31 MB); its external ONNX model weights are fetched only on request. Both provide suggestions for explicit owner review only.

`runonweb` and the `@browser-ai` AI SDK feasibility study are different projects. This PR uses only `runonweb/ocr`, not the Vercel AI SDK or a general-purpose in-browser LLM.

## Transactions: camera and receipt review

Open `/transacciones` → **Transacciones** → **Registrar compra o escanear ticket** → **Registrar compra**. This opens a focused optional-capture form. **The receipt is not required**: enter merchant, amount and date manually, or expand **Leer ticket o cupón (opcional)**. The existing **Agregar movimiento** form and its own optional OCR section still work.

Choose the payment method first (credit card, debit, transfer or cash):

- **Credit card:** choose the owning card and optionally enter installments, coupon/invoice/operation number and a note. The reviewed purchase is written as an existing `bankCardCharges` document (`countedInCashFlow:false`), never as an `expenses` document. The last-used card is remembered locally for the signed-in user; manual selection remains available. This is a purchase awaiting the statement, **not a reconciled statement item**. Never count it and the later statement payment together as two expenses.
- **Cash, debit or transfer:** the optional capture prepares the existing Transactions draft. The user then selects a category and explicitly confirms the real expense. No direct write occurs on this first capture screen.
- **Missing receipt, emailed invoice or card voucher:** all are valid. A photo is a convenience, not a prerequisite for either path. Printed invoice/coupon numbers are optional and currently preserved in the charge note or transaction description (within their existing length constraints). No new Firestore fields or permissions are required for this phase.

- Tap **Abrir cámara para sacar foto** to request browser camera permission **at that moment only**. Confirm the framing and tap **Tomar foto**; the video track stops immediately after capture or closing. On browsers without `getUserMedia`, the button opens the native photo capture picker (`capture="environment"`). The gallery picker always remains available, including on permission denial.
- Once a receipt image is chosen or a camera photo is taken, recognition starts automatically: no extra **Leer captura** click. Android/iOS default to **Compatible con celulares (recomendado)** — Spanish Tesseract worker and compressed language data on the same origin, independent of ONNX Runtime, whose v2 initialization still fails on some phones. Thermal receipts use single-block segmentation; bank and portfolio screenshots keep their original multi-column mode. Advanced OCR and retry controls live behind **Opciones del lector (opcional)**; Banks and Portfolio keep their existing explicit-review flows. All OCR outputs may contain mistakes.
- The receipt parser proposes only a plausible merchant, a **unique explicitly labeled total** (not subtotal, tax, change or several competing totals), a recognizable issue date and an explicitly labeled ticket/coupon/invoice/operation reference. It now supports numeric dates with two-digit years and abbreviated Spanish/English month names (for instance, `07/Nov/2026`), and skips `DOCUMENTO NO FISCAL` as a merchant. Missing or ambiguous values stay empty. The category is **never inferred**; a bare `$` does not prove ARS vs USD. The user must confirm the correct native currency.
- The receipt OCR now fills available fields **directly in the unsaved form** after recognition; there are no checkboxes or secondary **Aplicar campos** action. Missing/ambiguous values remain manual with one short message. Confirm the exact ARS/USD currency, amount and date before saving. If the chosen category currency contradicts the receipt, the Transactions form blocks submission and requests another category. Optional receipt numbers and notes stay collapsed unless requested or recognized. No Firestore schema/rules changes and no camera image or OCR transcript persists.
- Hiding financial values removes photo and text from the review UI and stops the camera. The app does **not** request camera access on page load.

The receipt photo and OCR text still do not persist or leave the device. Important limitation: thermal print, creases and occlusion can change digits (for instance `18.000` may be read as `16.000`). The user must verify the amount on the original document. In this first phase, separate ticket and payment voucher photos are not auto-merged or reconciled; do not create two purchases for the same transaction. A later phase will match reviewed credit purchases with statement PDF items.

## Banks: existing review and financial contract

**Finding the feature:** open `/bancos`, expand **Mis bancos**, and use the visible **Importar captura de consumos → Importar captura** shortcut above the list of banks. You need at least one registered card; the importer asks which bank/card receives the reviewed data. You no longer need to expand an individual bank and card to discover the feature. The original per-card entry remains available.

`CardConsumptionMarkdownImporter` offers **Desde captura** and **Pegar Markdown**. Both converge on the existing `parseCardConsumptionMarkdown` validator, explicit bank/card assignment, duplicate checks and `importReviewedCardConsumptionMarkdown` confirmation. A screenshot creates one reviewed **snapshot** (current card consumption) or one **charge** (individual purchase) at a time. For screenshots with multiple individual purchases, import separately or use the existing batch Markdown path (10 records maximum).

- The OCR adapter pre-fills only *unambiguous*, explicitly labeled `Consumos ARS/USD` and an explicitly labeled consultation date. A single dated merchant row with an explicit currency may also suggest one charge; multiple rows are never silently collapsed into one. Anything missing, ambiguous or error-prone is left blank for owner correction. Plain balances or card payments are never inferred as purchases.
- Current consumption is a card snapshot, not an `expenses` transaction. Approved individual charges remain `countedInCashFlow:false`. The existing deduplication, no-double-counting and native-currency rules are unchanged.
- All suggested amounts, dates, banks and cards are editable or chosen by the owner and must pass the original parser. The owner sees the original OCR text on demand and explicitly confirms before any Firestore write.
- Privacy mode hides the entire financial import/review UI and blocks new recognition and confirmation. Close/reopen resets ephemeral screenshot state.

## Portfolio: existing Markdown comparison

**Finding the feature:** open `/portfolio`, expand **Posiciones**, then use **Importar captura de inversión**. Choose an existing position or **Nueva posición** and click **Importar captura**; the existing editor opens with the OCR reader already expanded. This does not save data until you explicitly review, apply, and save the position. The original edit-form Markdown entry remains available.

The **new/edit position** modal includes the same local screenshot reader above its editable source-text field. Exact supported labels such as `Saldo actual`, `Cuotapartes`, `Valor cuotaparte`, `Tasa anual` and `Vencimiento` become explicitly labeled suggestions for the existing `parsePortfolioMarkdown` comparison. Source text remains visible for owner verification; unmatched fields are ignored.

The owner selects individual changes and clicks **Aplicar campos seleccionados** to update only the unsaved form draft; a separate **Guardar posición** persists the reviewed form. Balance changes never become earnings or withdrawals, no exchange rates are invented, and native currencies remain distinct. Privacy mode hides screenshot content and import proposals. No new Firestore fields or rules are required.

For a **fixed-term deposit** screenshot, the OCR normalizer recognizes explicitly labeled **Moneda**, **Vencimiento** (including two-digit years), **Fecha de valor**, **Tasa de interés nominal** and **Tasa de interés efectiva**. Tesseract's default plain-text output may list **all left-column labels followed by all right-column values**, so `tesseractLayout` reconstructs visual rows from word coordinates in TSV output before handing text to the **existing conservative parser**. This was checked locally against the owner's Itaú fixed-deposit screenshot (USD, 25/11/26, 28/05/26, 2,5%, 2,55%). The parser deliberately ignores **Intereses devengados** and **Intereses totales** as realized earnings or capital: accrued/projected interest is not a cash receipt or balance update. The owner still reviews every suggested field.

## Build compatibility

`runonweb@0.1.0` publishes TypeScript sources in its ESM exports. This cannot be parsed directly by LTC's Create React App 5 / Webpack configuration. `npm run prepare:browser-ai` uses a pinned `esbuild` dev dependency to bundle **only `runonweb/ocr`** to ignored `src/generated/browser-ai/` artifacts. The same preparation script copies the browser Tesseract worker, supported core WASM variants and compressed Spanish language data from locked npm packages to ignored `public/ocr-compatible/`. `prebuild` and `pretest` regenerate them; both engines are loaded dynamically on explicit interaction. Generated binaries must not be committed.

**Android compatibility fix (v2):** runonweb 0.1.0 hardcodes the ONNX Runtime WASM asset URL for **v1.30.0**, while its dependency range installs a newer JS runtime (e.g. **v1.31.1**). Its previous CDN workaround still required the user's Android browser/network to access jsDelivr, and could fail on restricted networks. The build now copies the *exact installed* WASM binaries into generated `/public/ocr-runtime/` assets and replaces the SDK hardcoded URL with the **same-origin** `/ocr-runtime/` path. Vercel/Netlify serve them from the deployment itself. Never commit generated binaries; `prepare:browser-ai` runs before tests and builds and the regression check asserts their signatures, sizes and generated path. The detector/recognizer ONNX model weights and dictionary still download from Hugging Face only after opt-in, and remain cached by the browser.

**Diagnosing mobile reports:** the panel explicitly identifies **Lector local v2**, so a screenshot that still says "aprox. 31 megabytes" / "No se pudo analizar" comes from an older loaded tab. Reload the page or close/reopen that tab after deployment before testing again. Error messages display safe categories without filenames, transcripts or backend URLs: `OCR-NET` = weights/dictionary network download, `OCR-MOTOR` = ONNX/WASM init, `OCR-MEM` = memory, `OCR-IMG` = image decode/inference, `OCR-TEXT` = no recognizable text, `OCR-INIT` = other setup error. If it still fails, record only the code, phone/browser model and whether Tiny was selected; do not collect private financial screenshots or raw errors. This workaround improves reliability but **does not prove** success on a real Android device without an actual on-device test.

**v3 Android remediation:** after the owner confirmed **Lector local v2** and **`[OCR-MOTOR]`** in Chrome Android, the issue is no longer attributable to stale deployment or only a blocked CDN. The compatible Tesseract worker is now the Android/iOS default, avoiding the broken ONNX initialization path. `OCR-COMPAT` identifies a distinct compatible-engine failure and leaves the original photo ready to retry or switch engines. This change ships independent worker + core + spa `traineddata.gz` from LTC's same origin. The initial load still takes time and memory; real-device acceptance must verify recognition and explicit review after merging. Privacy remains local-only.

**Fixed-term-deposit OCR enrichment:** a real Android test confirmed that the v3 engine recognizes Itaú fixed-deposit dates/rates, but the comparison displayed "no changes" because the existing dates and rates already matched and the adapter discarded bank-reported interest and contract metadata. The importer now recognizes explicitly labeled **intereses devengados**, **intereses totales previstos**, **número de contrato** and **renovación automática**. Portfolio review proposes four independent optional fields for positions categorized as **Plazo fijo**. Accrued/expected interest values are informational and are **never** interpreted as portfolio balance, credited yield, last earnings or realized earnings. The owner must select and apply the draft fields and explicitly save. The screenshot itself remains local; contract identifiers are hidden in the portfolio card while balances are masked. A repeated import with no differences correctly says the values already match, rather than implying OCR failed.

## QA and boundaries

- Test cold model download progress, cached/warm loading, WebGPU and WebAssembly on the production HTTPS preview. The SDK's own published timing figures were measured on a laptop, not an LTC user Android device.
- For v3, verify that Android defaults to **Compatible con celulares** (not the failing ONNX engine), and the same-origin assets under `/ocr-compatible/` return successfully. On desktop, manually switch engines to compare results. Capture status and progress without logging or uploading private screenshots.
- Test narrow widths (360/390 px), 1440/1728 desktop and both `html.dark` themes. Verify focus, 44px targets, disabled/error/progress states, privacy reveal/hide and no horizontal overflow.
- Use synthetic screenshots first, then explicit owner-supplied bank/portfolio screenshots. Check Argentine `1.234,56` separators, ARS/USD independently, OCR errors (`0/O`, `1/I`, decimal mark), date conversion, multi-card ambiguity and retries.
- Reject images other than PNG/JPEG/WEBP or larger than 8 MiB. Never persist the file, extracted raw text or credentials, and never log private OCR output. If the SDK fails or a browser cannot run it, the original manual/Markdown import path remains available.
- All browser AI output is **untrusted suggestion text**. It cannot call a bank, update balances automatically, change categories or create a transaction without owner review.
